Stakeholders：
The stakeholders involved in this game include:
	•	Players – people who play the game and interact with the system.
	•	Game Developers – responsible for implementing the game mechanics and features.
	•	Game Designers – responsible for gameplay experience and difficulty balancing.
	•	Project Manager / Team Manager – oversees development progress and ensures project goals are achieved.
	•	Testers – team members or users who test the game to find bugs and usability issues.
	•	Gaming Community – potential players who may use the game after release.

Epics:
User Story 1 – Controlling the Spaceship

As a player
I want to control the spaceship using keyboard inputs so that I can move around the screen and avoid asteroids.

Acceptance Criteria
Given the game has started,
When the player presses the movement keys,
Then the spaceship moves in the corresponding direction.

User Story 2 – Shooting Asteroids

As a player
I want to shoot bullets from my spaceship so that I can destroy asteroids and survive longer.

Acceptance Criteria
Given the spaceship is active in the game,
When the player presses the shoot key,
Then a bullet is fired from the spaceship.

User Story 3 – Scoring System

As a player
I want to see my score increase when I destroy asteroids so that I can track my progress in the game.

Acceptance Criteria
Given the player destroys an asteroid,
When the asteroid is removed from the screen,
Then the player’s score increases.
Given the score changes,
When the game updates the interface, then the updated score is displayed.

Reflection:
During this requirements exercise, our team identified the key stakeholders involved in the development and use of the game. Understanding the stakeholders helped us think about who will interact with the system and who benefits from its functionality.
Creating epics allowed us to define the main features of the game, such as controlling the spaceship, shooting asteroids, and tracking the player’s score. Breaking these epics down into user stories helped us focus on the player’s perspective and clearly describe what functionality the system should provide.
Writing acceptance criteria also helped us define how each feature should behave and when it should be considered complete. This makes it easier to test the system and ensure that the implemented features meet the intended requirements. Overall, this process helped our team better understand the structure of the project and organize the development tasks more clearly.
